## 📍 Current State

The local model server now runs with a **65536-token context** (was 32768), and
both PowerShell entry-point scripts log errors to files for after-the-fact
review.

### Background (the error that triggered this)
`run-full-pipeline.ps1` failed during the research condenser with:

```
openai.BadRequestError: Error code: 400 -
{'error': {'message': 'request (34383 tokens) exceeds the available context size
(32768 tokens), try increasing it', 'n_prompt_tokens': 34383, 'n_ctx': 32768}}
```

The Qwen3.8-27B GGUF metadata (`qwen35.context_length`) advertises a native
context of **262144** tokens, so no RoPE scaling is required — the server was
simply started too small.

### What was added
1. **`scripts/start-model-server.ps1`**
   - `-CtxSize` default raised `32768 → 65536`; documented why and how to tune.
   - New `-ServerLog` parameter (default `logs/llama-server.log`) passed to
     llama.cpp via `--log-file`, so server-side errors are persisted.
   - Inline comments added to every parameter.
2. **`scripts/run-full-pipeline.ps1`**
   - Inline comments added to every parameter (plus comment-based help).
   - New `-LogPath` (full run log, default `logs/run-full-pipeline_<ts>.log`)
     and `-ErrorLogPath` (default `logs/pipeline-errors_<ts>.log`).
   - Pipeline stdout **and** stderr are **streamed line-by-line** to the console
     while being appended to the run log as UTF-8, so progress is visible during
     a long run and `Ctrl+C` (safe, resumable) remains possible. Python runs with
     `-u` / `PYTHONUNBUFFERED` so it does not block-buffer the pipe.
   - On failure (non-zero exit or exception) a database error report is written
     before exiting, and the log paths are printed.
3. **`scripts/pipeline_error_report.py`** *(new)*
   - Reads `community_condenser_runs` + `community_pipeline_status` and prints a
     plain-text error report. Reusable standalone.
4. **`modules/community/full_pipeline.py`**
   - `_force_utf8_stdio()` (UTF-8 stdout/stderr) — see the exit-code fix below.
   - Heartbeat: each condenser runs as a task while the pipeline logs a
     `⏳ still working on <community> / <condenser> (Ns elapsed)` line every
     30s (`PIPELINE_HEARTBEAT_SECONDS`, `0` disables). This is what tells an
     operator a long model call is still alive.

## 🐛 Exit code 1 — root cause fixed

The first real run still exited 1, but the run log showed it was **not** the
context error:

```
UnicodeEncodeError: 'charmap' codec can't encode characters in position 13-72
```

The pipeline logs box-drawing glyphs (`─`) and status icons (`▶ ✓ ✗`); the
Windows console uses cp1252, so `print()` raised and aborted the whole run.

Fixes:
1. `modules/community/full_pipeline.py` — `_force_utf8_stdio()` reconfigures
   stdout/stderr to UTF-8 with `errors="replace"` at the start of `_main()`, so
   the CLI is safe on any console (direct `python -m ...` runs included).
2. `scripts/run-full-pipeline.ps1` — sets `PYTHONUTF8=1`,
   `PYTHONIOENCODING=utf-8` and `[Console]::OutputEncoding = UTF8` before
   launching Python, so the run log is captured cleanly too.

Also fixed: the script's inline summary/review-queue snippets interpolated
`$DbPath` straight into Python source, so a Windows path containing backslashes
(`C:\...`) produced an invalid `\U` escape / `SyntaxError`. Both now pass the
path as `sys.argv[1]` instead.
